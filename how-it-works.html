How It Works

How the Operations Center is built and run, in plain English. For anyone joining the work on the site. No code, passwords or keys here.

The big picture

The site is made of four outside services. None of them run on a company computer, and there is no server of our own to look after.

Your browserLoads the pages, signs you in, and talks straight to Supabase for data. All the screens are plain web pages.
CloudflareOwns the liquidtrucking.io domain and hosts the website at www.liquidtrucking.io. Sends out the pages and data files.
SupabaseSign-in, the database (users, map colors, FAQs, feedback, all history) and private file storage. The rules for who can read or change what live here.
GitHubHolds the site's files and their full history. Cloudflare publishes the site from it automatically.
ResendSends email from liquidtrucking.io: sign-in codes, and the alert to the owner when feedback comes in.
ClaudeMakes the changes Jason asks for in the project, as pull requests on GitHub, and keeps What's New and this page up to date.

Open www.liquidtrucking.io→Cloudflare sends the page→Browser asks Supabase "who is this?"→Supabase returns only what that person may see→Page shows it

Who can see and do what

  • Owner: one account (Jason), set only in the database. Only the owner can make or remove admins, change another admin, view as another admin, or delete feedback and FAQs. Nobody else can change the owner's account.
  • Admins: see and edit every page, and manage users on the Admin page.
  • Users: get access page by page: No access, View, or View + edit. What's New and How It Works only offer No access or View.
  • Active / inactive: turning someone inactive shuts them out everywhere without deleting their history.
  • Public: a page set to Public on the Admin page can be seen by every signed-in, active user. Nothing is ever shown to people who aren't signed in, apart from the sign-in page.
  • View as: an admin can see the site exactly as another user does, read-only. Each start and end goes into Account history.

Where the rules are enforced

The rules are checked in two places. The browser uses them to decide which menus, tiles and buttons to show. The database checks them again on every read and every change, so hiding a button is never the only thing standing in the way. This is why changes go through named database functions (for example "save a county color") rather than editing tables directly: each function checks the person's access first and writes the history.

Worth knowing: the site's files on GitHub are public. That's normal for this kind of site, because the database holds everything private and checks every request. But it means the text of What's New and this page, and the site's code, can be read by anyone who finds the GitHub page. Never put passwords, keys or private details in the site's files.

Files (screenshots, videos, PDFs) live in two private storage areas, feedback and faq. They can only be opened by signed-in people allowed to see them. FAQ files are never deleted, so older versions keep working.

History is kept, not overwritten. Map colors, FAQs, feedback and accounts all keep a permanent record of who changed what, when and why. Deleting feedback or an FAQ only hides it, and the owner can restore it.

On the website itself

  • Map data files: state and county outlines (U.S. Census), highways (Natural Earth), cities (GeoNames) and ZIP codes. These are free public data and rarely change.
  • Starting map colors: the colors from before the map moved into the database, used as a fallback.
  • What's New: the list of updates, written by Claude.

Sign-in and email

  • Sign-in is by email only: Supabase sends a 6-digit code, with the subject "Your Operations Center sign-in code". There are no passwords. Codes rather than links are used because work email filters were using up sign-in links before people could click them.
  • Supabase sends those codes through Resend, from no-reply@liquidtrucking.io. The liquidtrucking.io domain is verified with Resend so the mail isn't treated as spam.
  • New feedback triggers an email to the owner, sent from the database through Resend. The Resend key is stored in Supabase's encrypted Vault, never in the site's files.
  • If an email doesn't arrive, check Junk or Quarantine in Outlook first. For feedback alerts, the email log table shows what happened.

How a change gets made

Jason asks in the Claude project→Claude builds it on its own branch→Pull request on GitHub→Jason merges→Cloudflare publishes it in about a minute→Run SQL, if any
  1. Every change starts as a request. Claude makes it on a separate copy (a branch) and opens a pull request (PR) describing what changed and how it was tested.
  2. Nothing reaches the live site until Jason presses Merge on GitHub. Cloudflare then publishes the new version automatically.
  3. If the change needs the database to change, it comes with a numbered SQL file. Jason runs it once in the Supabase SQL Editor. The files are written so running one twice does no harm.
  4. The same PR adds a What's New entry, and updates this page when how the site works changes.
GitHub shows a red ✗ for "Workers Builds" on pull requests. That's Cloudflare's preview build for branches, and it has failed on every PR so far. The live build that runs after merging works. It's safe to ignore until someone looks at it in Cloudflare.

Undoing a change: GitHub keeps every version, so any merged PR can be reversed with GitHub's "Revert" button, which goes live the same way. Database data (colors, FAQs and so on) is protected by the history tables and Supabase's own backups.

How the files are organized

The site is plain web pages: there's no build step and no app server. Each page is one file, and a few shared files hold what every page uses.

  • One file per page, with each department in its own folder (for example, the Recruiting pages are in recruiting/).
  • The site map (assets/nav.js): the list of departments and pages, the shared header, menu and footer, the "who can see what" rules the browser uses, and View as.
  • Sign-in helpers (assets/portal.js), the feedback button (assets/feedback.js), and the look (assets/site.css: the liquidtrucking.com colors and fonts).
  • Data files in data/, and database setup files in supabase/.
  • README and CLAUDE.md: technical notes for whoever works on the site. These, and the SQL files, are kept off the live site.

Adding a page or a department

  1. Add the page file to its department's folder, using the same header and footer as the others.
  2. List it in the site map, under its department.
  3. Add its row to the pages table with a small SQL file, so admins can control access to it.
  4. If it stores anything, add its tables with access rules and history, plus functions for every change.
  5. A new department just needs its own folder and an entry in the site map. It shows up on the dashboard once someone can see one of its pages.

Bringing someone onto the dev work

  1. Site account: add them on the Admin page, and give them View on What's New and How It Works.
  2. GitHub: invite them to the liquidtruckingcompanies/recruiting repository. "Write" lets them open pull requests. Keep merging to the owner, or to someone trusted.
  3. Supabase: only if they need the database. Invite them to the organization with the lowest role that works. They'll be able to see real data.
  4. Cloudflare and Resend: usually not needed. Only for domain, hosting or email changes.
  5. Where to start: this page, then What's New for recent history, then the README and CLAUDE.md on GitHub.
  6. Ground rules: every change goes through a pull request; database changes come as new numbered SQL files (never edit an old one that's already been run); every visible change gets a What's New entry; and no passwords, keys or private details in the files.
  7. Trying changes: any simple local web server works, because the site is plain files. It uses the real database, so test with care, and use View as to check what other people see.

Words you'll see

  • Repository (repo): the folder of site files on GitHub, with every past version.
  • Branch: a separate copy for working on a change without touching the live site.
  • Pull request (PR): a proposed change, shown as a list of edits to review before it's merged.
  • Merge: accepting a PR into the main copy, which publishes it.
  • Deploy: publishing the site. Cloudflare does it automatically after each merge.
  • SQL / migration: instructions that set up or change the database. Ours are the numbered files.
  • Row-level security: the database rules that decide, row by row, who can read what.
  • Database function: a named action, such as "save a county color", that checks access and writes history in one step.
  • Publishable key: the public key in the site's files that lets browsers reach Supabase. It's meant to be public: on its own it can only do what the security rules allow.
  • Vault: Supabase's encrypted store for secrets, like the Resend key.
  • Worker: Cloudflare's name for the service that hosts the site.
